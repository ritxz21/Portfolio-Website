## The problem

Large industrial companies accumulate databases the way houses accumulate
boxes in the attic. Manufacturing data here, sales data there, service
records somewhere else — each with its own schema, its own naming
conventions, and its own person who understands it.

The people who need answers are rarely the people who can write SQL. A
product manager who wants to know how a component performed across regions
last quarter has to find an analyst, explain the question, wait, and then
usually explain the question again because something got lost in
translation. The bottleneck isn't the data. It's the translation layer, and
that layer is a person.

I spent six months at Atlas Copco building two systems that attack that
bottleneck from opposite ends: one that lets people ask questions directly,
and one that makes the underlying data models legible in the first place.

## Asking questions in English

The first system is a natural-language-to-SQL agent. Someone types a
question the way they'd ask a colleague, and gets an answer back — no SQL,
no ticket, no waiting on an analyst.

The hard part isn't generating SQL. Language models do that readily. The
hard part is generating SQL that is *correct* against a real enterprise
estate, where the relevant tables live in different databases and the same
concept wears a different name in each one.

Plain retrieval struggles here. If you search the schema for text similar to
the question, you get tables that *sound* related. But which table actually
joins to which, and on what key, is structural information — and similarity
search throws structure away. So the agent uses GraphRAG: the schema is
represented as a graph, with tables as nodes and their relationships as
edges. Retrieval walks that graph from the entities named in the question
to the tables that hold them, following joins that genuinely exist rather
than joins a model inferred from column names that happened to rhyme.

<Callout kind="decision" title="Why a graph rather than plain retrieval">
A vector search over schema text answers "which tables sound like this
question?". A graph answers "which tables are actually connected, and how?"
For a single clean warehouse the first is enough. Across several databases
with inconsistent naming, it isn't — the join path is the answer, and it's
exactly the part flat retrieval can't see.
</Callout>

The output is a query the user never sees and an answer they do. The point
was never to teach people SQL. It was to remove the step where they need it.

## Documenting PowerBI, for a NASA client

The second system came out of a client engagement with NASA, and it started
from a complaint rather than a spec.

PowerBI reports accumulate the same way databases do. Someone builds a
dashboard, defines forty measures, and eventually moves on. The measures
still work. Nobody remembers what they mean. The documentation, if it
exists, was written once and has been quietly wrong for a year.

So I built an agent that reads the data model directly and generates
structured documentation from it — what each measure computes, what it
depends on, how the tables relate — and then lets people query that
documentation in natural language. Asking what *utilisation rate* actually
measures returns an answer grounded in the model itself, rather than in a
wiki page someone forgot to update.

## What I took from it

Both systems are the same idea pointed at different targets: the
organisation already knows the answer somewhere, and the work is building
something that can find it and say it plainly. Neither one is a model
problem. They're retrieval problems wearing model-shaped clothes, and most
of the effort went into representing what already existed well enough that
a language model could reason over it without guessing.
